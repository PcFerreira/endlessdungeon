# Persistent world server

The first online slice supports accounts, persistent character profiles, shared movement and Worldgate travel. A headless Godot process uses `HubWorld` to add Lanternwake to production World terrain and collision. Fresh accounts start at its authoritative arrival; existing saved positions are restored and validated. The Node gateway owns account access, durable records, connection limits and nearby player snapshots. Combat, loot, stores, interiors and building require additional authoritative handlers before they can be enabled online.

## Local development

Run commands from the repository root with Node 24. The existing local engine is selected automatically on macOS. Linux deployments must set `GODOT_BINARY` to the matching headless Godot executable.

```sh
PATH="$PWD/.tools/node/bin:$PATH" npm ci --prefix server --ignore-scripts
ruby tools/build_network_manifest.rb --check
PATH="$PWD/.tools/node/bin:$PATH" node server/index.mjs
```

The endpoint is `ws://127.0.0.1:8080/play`; `/ws` remains a compatibility alias. `GET /healthz` reports readiness, player count and current tick. Development binds `0.0.0.0`, accepting connections on all IPv4 interfaces, and stores SQLite data in `server/data/world.sqlite`. The Web host also binds all interfaces on port 8000. The custom single-thread Web launcher supports login/play at `http://SERVER_IP:8000/` in silent LAN test mode. HTTPS/WSS retains normal audio; public HTTP hosts keep the secure-context requirement. Native clients may use private-LAN WebSockets in development. Replace `SERVER_IP` with this machine's LAN address. `ENDLESS_DB`, `ENDLESS_PORT`, `ENDLESS_HOST`, `GODOT_BINARY`, `MAX_PLAYERS` and `INTEREST_RADIUS` are configurable. To isolate a run, use `ENDLESS_DB=/tmp/endless-online/world.sqlite`. `WORLD_SEED` selects the signed 32-bit seed on first creation; a later different value is refused. Existing worlds retain their saved seed and generator edition across restart.

Authentication uses 3-24 ASCII letters, digits or underscores for usernames and 12-128 characters for passwords. Usernames are case insensitive. The server stores salted scrypt password hashes and SHA256 hashes of opaque session tokens. Tokens expire after seven days. A fresh login rotates all prior tokens. Resuming the same token or signing in elsewhere replaces the prior live connection. Each account has one character and its class is selected at registration.

## Authority and persistence

Protocol 1 authentication messages are `register`, `login` or `resume`, with the current `content_revision`. Registration adds `username`, `password` and `class_id`; login supplies username/password; resume supplies the returned `token`. A `welcome` contains the owning player's profile/build/inventory/position and the saved world identity. Public player records contain only ID, username, class, profile, position and heading.

Movement input is `{ "type": "input", "seq": 1, "direction": [0, 1] }`. Sequences increase within a connection and direction length cannot exceed one. The worker advances at 20 fixed ticks per second and 3.8 world units per second. Missing input stops movement after 500 ms. Clients cannot supply positions, elapsed time, inventories, rewards or generic save packets. Unknown commands and extra input mutation fields are refused.

Authenticated `hub_travel` messages carry only `destination: "world"` or `destination: "hub"`. The worker requires the player to stand beside the actual departure gate, selects a supported destination, stops movement and returns the new authoritative position. The gateway persists it before acknowledging travel. Malformed or off-gate requests return a nonterminal refusal; genuine authority/storage failures retain fatal handling. The browser receives destination chunks before showing its player there, and generates no destination terrain.

Online terrain is generated only by the worker and delivered as immutable map chunks. After welcome and each chunk crossing, the gateway sends nearby 16-by-16-cell chunks within a radius of two, with encoded real region metadata. The wire message is `{ "type": "chunks", "revision": "...", "chunks": [{ "coordinate": [4, 4], "cells": {} }], "regions": [], "radius": 2 }`; cells/regions use the shared tagged `MapChunkCodec` format. Each message contains one chunk and stays under 1 MiB. Clients may request up to 25 nearby coordinates with `{ "type": "chunks", "coordinates": [[4, 4]] }`. Malformed, excessive or absolute out-of-bounds coordinates are rejected. Valid requests based on an older player snapshot are filtered to the current authority radius without an error; automatic streaming supplies the current window after a boundary crossing. Unrequested remote chunks are never delivered. SQLite stores chunks and regions by world ID, revision and coordinates. Revisits and restart read these records before generating missing data. Old revision records remain available for rollback; changed releases create a separate cache namespace after explicit upgrade. Map downloads contain no account secrets or inventory records.

SQLite uses WAL, full synchronous writes and transactions. Connected player snapshots are written each second, at disconnect and during graceful shutdown. An abrupt process or machine failure can lose up to approximately one second of movement; accounts, committed character records and tokens remain durable. Database errors or authority-worker failure stop the gateway. Each live player has a bounded streamed Godot World instance with the same seed/edition; this avoids exchanging one player's collision window for another's. Region and route caches are cleared periodically. Nearby snapshots use an 80-unit default interest radius.

The network manifest pins protocol, generator edition, engine version and production content hashes. The worker's actual engine handshake must match the pinned engine. Startup rejects stale inputs, mismatched world seeds and changed content revisions. To adopt new verified content, stop the world, back up its database, rebuild/check the manifest and run `node server/index.mjs --upgrade-content`. This preserves account/world IDs and seed, updates the explicit revision and validates persisted positions against the new map on next login. Generator-edition and protocol changes require a separate migration. Browser and server deployments must use the same release.

The gateway and worker can execute editions 4, 5 and 6 when an explicit matching manifest/world is supplied. This allowlist preserves edition 4 as the public manifest default and retains existing database editions. `--upgrade-content` cannot change an existing world's generator edition.

## Public deployment

No public host or domain is configured yet. `Dockerfile`, `compose.example.yml` and `Caddyfile.example` provide deployment examples; Docker is unavailable on the development machine, so container execution and live HTTPS remain untested. Set `GAME_DOMAIN` to your actual domain, export the browser release into `builds/web`, then use `docker compose -f server/compose.example.yml up --build -d`. Compose pins the world service to `linux/amd64`; a direct Docker build must also use `--platform linux/amd64`. Caddy serves the browser and proxies `/play` with automatic HTTPS. Keep the Node service internal to that network.

The image defaults to the official [Godot 4.7.2 Linux x86_64 archive](https://github.com/godotengine/godot-builds/releases/tag/4.7.2-stable), with SHA256 `cadd3204e728a35d3f13adb7fd0d7902636b79f6b95c40c265eb73b6c35329e4`. The downloaded 77,860,424-byte archive was checked against the official release API digest. `GODOT_URL` and `GODOT_SHA256` can override these defaults for a verified mirror of the same pinned engine. The Docker build verifies the hash before installing the binary and retains its upstream MIT license, author list and third-party copyright notices in `server/GODOT_{LICENSE,COPYRIGHT,AUTHORS}` files. Its actual engine handshake must match the deployed manifest.

The build uses `assemble_runtime.mjs` to create a separate filesystem with every manifest input, production scripts/configuration, all asset catalogues, lore locales and worker static preload resources. Assembly verifies input hashes and copies actual files instead of source-directory symlinks. `Dockerfile.dockerignore` restricts the build context to metadata/code; `server/data`, local `node_modules`, staged downloads, browser builds and user saves are excluded. The final image copies only that assembled runtime and installs its own locked dependencies. No live database or local dependency tree is copied into the image.

Development defaults allow browser origins on port 8000 for localhost, this server's hostname and its current IPv4 addresses. Native clients may omit Origin in development. `ALLOWED_ORIGINS` overrides that list; when supplied, missing and unlisted origins are rejected. `PUBLIC_WORLD=1` requires an explicit `ALLOWED_ORIGINS` list, including when Node binds localhost behind a proxy. The compose example allows only the configured browser origin. `TRUST_PROXY=1` accepts a single valid `X-Forwarded-For` address supplied by that trusted proxy; enable it only when clients cannot reach Node directly. The gateway limits payloads, connections, authentication attempts, concurrent scrypt jobs, input frequency and outbound backpressure, and disconnects clients that fail heartbeat or sign-in deadlines. Passwords and tokens are excluded from logs. Public-operation work still includes backups, monitoring, account recovery/moderation and a measured concurrency/load budget.

Use SQLite's backup API or stop the service before copying its database. Copying only the main SQLite file during WAL writes can omit committed records. Keep backups and the exact release/manifest together.

## Acceptance

```sh
PATH="$PWD/.tools/node/bin:$PATH" npm test --prefix server
PATH="$PWD/.tools/node/bin:$PATH" npm audit --prefix server
```

The integration fixture launches the real gateway and headless worker, verifies the actual engine version and uses two actual WebSocket clients. It receives all 25 initial chunks, checks their 256 encoded cells and region metadata, and compares persisted chunk payloads after restart. Shared movement/speed, unauthorized/forged/stale input, malformed JSON, oversized-payload closure, distant-player interest, durable profiles/inventories/tokens, duplicate-session replacement and old-credential/revision rejection are covered. A blocked cell discovered in the real generated world stops actual server movement. Explicit content upgrade preserves IDs/seed, while stale manifest input hashes refuse startup. Tests use an isolated temporary SQLite database and do not modify local journeys. Browser/native rendering, container execution, public HTTPS and concurrency load testing remain separate acceptance.

Collision and lagged boundary probes use the actual HubWorld provider and hub arrival. `floating_city.test.mjs` exercises two fresh co-spawns, unauthenticated/malformed/off-gate refusal without shutting down either session, physical gate approach, departure/return, peer interest and persisted restart. These gameplay fixtures bind explicit loopback addresses. `network_binding.test.mjs` separately checks the default all-interface listener through its actual LAN IPv4 address, real allowed/disallowed WebSocket origins, development native clients and explicit public-mode origin requirements. Same-machine LAN-address checks do not certify another device's firewall or Internet path.

`test/runtime.test.mjs` invokes the same assembly used by Docker into a temporary directory outside the checkout, checks complete manifest/catalogue coverage and containment, installs independent dependencies there, and launches the real gateway/worker with that directory as the project. Real registration produces valid character/inventory snapshots and generated chunk/region data. This verifies the deployment resource closure with the installed macOS engine; it does not claim execution of the Linux image or its OS libraries.

The gateway dependency is [ws](https://github.com/websockets/ws). Persistence uses [Node 24 SQLite](https://nodejs.org/docs/latest-v24.x/api/sqlite.html); password hashing uses [Node crypto scrypt](https://nodejs.org/docs/latest-v24.x/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback). Deployment proxy behavior is documented by [Caddy reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy).
